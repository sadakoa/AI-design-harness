Support inbox — proposal

2026-10-07 · PRD: _inputs/prd.md · Improvement

1. Problem

Support agents who handle 50–100 requests a day open the inbox and see everything by date, so a high-priority request can sit under routine ones and get missed. The list should open on what's urgent and let agents hand requests to the right person, one or several at a time.

This improves a list that already exists, so it ends with a recommendation. The design system still has placeholder content: principles.md, the word table in writing.md, components/GUIDE.md and the feedback log are marked "(example)". P-01 to P-03 and the word table are used as written here, but they need replacing before these decisions carry weight.

5. Options

A: Priority groups

One table grouped High, Medium, Low, with a count on each group. Inside a group, the request that has waited longest comes first. Every row shows subject, customer, status, assignee and received time. Assign from the row, or select several and assign them once. Good: the shape of the screen is the priority, so urgent requests can't sink, and the summary line says how many high-priority requests have no assignee. Weak: a request that's already in progress can still sit at the top of its group, and the table needs about 900px before it has to scroll sideways.

Open on its own · States: loading · empty · error · done

B: Unassigned and team

Two panels. On the left, unassigned requests as cards, highest priority first. On the right, everyone's assigned requests grouped by person with an open count, fewest first. Good: you can see who has room before you assign, and nothing unassigned can hide. Weak: priority turns into a label on a card instead of the order of the whole screen, the two panels compete for attention, bulk assign only works on unassigned requests, and reassigning hides in small rows.

Open on its own · States: loading · empty · error · done

C: Triage with preview

A compact list in priority order on the left. On the right, the current request: assignee, customer, received time and the latest message. J and K move, X selects, A assigns, 1–5 picks a person. Good: fastest for agents who live on the keyboard, and you can read the message before you assign. Weak: the right panel is a preview of the detail page the PRD leaves out of scope, priority is only an icon in the narrow list, subjects get cut off, and the shortcuts favor experienced agents.

6. Recommendation A

The PRD's problem is that urgent requests get missed because the list only knows about dates. Option A turns priority into the structure of the list: High is always on top with its count, and the line under the title says how many high-priority requests have no assignee. That follows P-01 One screen, one main thing: the screen does one job, showing what to work on in order, and nothing competes with it. It also keeps to P-02: each row has the six fields the PRD asks for and nothing else. Assigning is visible on every unassigned row, and several requests can be assigned in one go from the selection bar, which covers both "Must support" items.

Why not the others

  • B: Answers "who has room?" better than "what's urgent?". Priority becomes a label inside a card, in-progress requests lose their priority order, and two panels pull attention in different directions (P-01). Worth keeping: the open count per person, which A already shows in its assign menu.
  • C: Good for keyboard-heavy agents, but its side panel previews the detail page the PRD puts out of scope, and it shows one request at a time, so comparing urgency means scanning a narrow list with only icons. Leading with shortcuts also makes it harder for agents who are less at ease with software (principles.md, "Who it's for"). Worth keeping for later: J, K, X and A as an extra on top of A.

7. Spec

Structure

In order:

  1. App bar: product name and the signed-in agent.
  2. Page header: the title "Inbox" and one summary line with the open count and how many high-priority requests have no assignee. It tells agents where to look first.
  3. Views: tabs for Open, Unassigned, Assigned to me and Done today, each with a count.
  4. Toolbar: the sort order and a hint for bulk assigning. Once rows are selected, it becomes "N selected · Assign · Clear selection". Search sits on the right.
  5. List: one table with columns for selection, request (subject, then customer and company), status, assignee and received time. It's grouped High, Medium, Low, with a select-all and a count on each group.

Toasts "Assigned N requests to Priya Raman.", "Assigned N requests to you.", "Removed the assignee from N requests." Dates look like "Oct 7, 2026, 10:52 AM".

Edge cases

  • Lots of requests: at 100 or more, the groups stay and each keeps its count. Collapsing Low by default is an open question.
  • Selection and switching: changing view or searching clears the selection, so nobody assigns rows they can't see. Select-all only covers the current view and search.
  • Assigning in Unassigned: the rows leave the view. The toast confirms the change, and Undo brings them back.
  • Mixed selection: if the selected rows have different assignees, the menu shows no tick. "Remove assignee" appears if any of them has one.
  • Two people assign the same request at once: open. Today the last change wins, which needs a decision.
  • Long subjects and names: cut off with an ellipsis, with the full text on hover.
  • No permission to assign: open. For now we assume everyone can (question 1).
  • Leaving halfway: the selection isn't kept, but nothing is lost, because each assignment saves right away.
  • Team size: we assumed 5–15 people. Past about 10, the menu needs a search box.
  • Narrow windows: below about 900px, the table scrolls sideways (review #7).

8. Feedback for the design system

What the design system didn't have, rules we broke, and what the review found. IDs from work/feedback.md. Full review: review.md. In this example run, new entries aren't added to the log; they're listed under "Would log" in review.md and would take the next free IDs.

  • FB-01 (example, carried over): one primary action per screen. A keeps to one: "Assign" only once rows are selected, and "Try again" only in the error state.
  • Would log, missing: no component specs for the table with group rows, the assign menu, the toast, or the priority and status indicators. They were built in work/.
  • Would log, missing: no priority colors. color.status.danger and color.status.warning stand in for high and medium (review #3).
  • Would log, insight: secondary text on the selected-row wash is about 4.3:1, and rules.md has no contrast rule (review #4).
  • Would log, missing: no token for loading placeholders (review #5).
  • Would log, missing: no word for taking an assignee off, because "Remove" is reserved in writing.md (review #6).
  • Would log, missing: no elevation for menus and toasts (review #8).
  • Would log, missing: only one date format, while lists need a short one for today (review #9).
  • Would log, insight: a list's main per-row action has to be visible without hovering (review #1, fixed here).

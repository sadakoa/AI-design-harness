AI Design Harness

Check you're building the right thing, then design it the way your team would — with AI agents like Claude Code or Codex.

github.com/sadakoa/AI-design-harness

A small starter kit for teams where people and AI agents design UI together. It is a repo of plain files: what you know about the product, your design rules, five skills that use them, and a check script.

WHY

Why it exists

What we know about users and our design rules usually live in people's heads. The harness writes both down as small files, plus five skills (saved instructions like /frame) and a check script, so an AI agent can follow them.

Today

❌ PRDs aren't checked against what we know

❌ One long doc mixes rules and one-off calls

❌ Review comments are opinions, not rules

❌ Lessons get lost in old chat threads

With the harness

✅ Each PRD is checked against users and jobs

✅ One question, one file

✅ Findings cite a rule, or say it's taste

✅ Lessons flow back into product and design

AI Design Harness

2

The most expensive mistake is a clean design for the wrong problem, and nobody checks a PRD against what the team already knows. On top of that, the usual setup is one long design document. It mixes everything and drifts. Review comments are opinions with no rule behind them, and what a review teaches rarely makes it back. The harness is a template repo that fixes those four things: a check before design, small files with one job each, reviews tied to named rules, and a log that turns lessons into changes.

WHAT YOU GET

One proposal per screen or flow

A framing first, then about three clickable mockups, a recommendation and a spec on one HTML page, reviewed against your rules. Your team still decides, and builds it.

AI Design Harness

7

Building and reviewing are different jobs, so they read different things. Building reads the product entries the framing cites plus the design files, and spreads out into a few real options. For a flow, each option holds every screen and the links between them work. Reviewing first asks whether the design does the job from the framing, then checks one area at a time — components, layout, then copy, meaning the UI text — and only re-reads the files for that area. Every finding points to a rule or principle ID.

AI Design Harness

8

Every finding starts open in work/feedback.md, including observations from support tickets, analytics or interviews. Once a week promote-feedback groups them and suggests where each should go, but an owner decides. Adopted ones change product/ or the design system in a pull request, and the decisions file next to it gets a row. Promote when it came up on two or more screens, or the same rule was broken twice, and you can name the one file where it belongs. Screen-only ones stay with that screen. Dropped ones keep their row and the reason.

IN PRACTICE

Running it as a team

Owners are the people in CODEOWNERS: product owners for product/, design owners for design-system/.

First months

Only owners change product/ and the design system. Collect findings first.

Then

Designers open PRs too. Start with UI text rules (writing.md).

Every week

An owner runs promote-feedback and decides.

Approvals

With two or more owners, require their approval on GitHub.

NOT FOR

Screens unlike anything your product has today. The agent drafts options; someone with design experience should finish them.

design-builder starts by framing the PRD and stops if the framing says stop. Then it walks through what a designer does in their head. The important part is step 5: options have to differ in structure, like list-first versus detail-first, not just in color. For a brand-new kind of screen it stops at the options and a person picks. You'll answer up to five questions along the way.

APPENDIX

What the check catches

npm run check runs on your machine and on every pull request.

File missing from an INDEX

In product/ or design-system/, or its Answers line doesn't match

Out of sync

Your code changed since the last npm run sync

Off-token CSS

Hard-coded colors or unknown CSS variables (R-01)

Duplicate IDs

Two entries share an ID: U-, J-, PD-, R-, FB- and the rest

Fact or guess?

A user or job not marked fact, hypothesis or open

Stale notes

Not reviewed in 90 days

AI Design Harness

14

If a machine can catch it, the machine should. The check has no dependencies. Lines you tag with a feedback ID are skipped on purpose, so breaking a rule is allowed as long as it is recorded. With sync.json, it also fails when your product's code has changed and the harness hasn't caught up.
